# 多智能体信箱协议（Multi-Agent Mailbox Protocol）

[English](README.md) | **简体中文**

一套轻量协议：让**不共享记忆、不共享上下文、不在同一运行时**的 AI 智能体之间交接任务——只靠共享文件。

没有服务器，没有 SDK，没有消息队列。只要两个智能体能读写同一个文件夹（云盘、共享文档、Git 仓库），就能用这套协议协作。

> 适用于协调者与被调度方互不共享记忆、上下文和运行时、只能通过共享文件传递工作的场景。每一次派发，都有一份可核验的回执。

## 为什么用信箱？

大多数多智能体演示都假设有一个统一框架：一个运行时、一个调度器、共享状态。现实要乱得多：

- 你的智能体住在**不同的产品**里，账号各不相同；
- 有的只能通过**文档**或**聊天窗口**触达；
- 有的靠**定时**醒来，而不是推送唤醒；
- 有些步骤（登录、付款、发布）必须留在**人工闸门**后面。

文件信箱是能贯通所有这些场景的最小公分母。它天生就慢——但没关系，它承载的工作（调研、起草、分析、批量执行）本来就是异步的。

## 三种通道

协议与载体无关，规范定义了三种通道：

| 通道 | 载体 | 适用场景 |
|---|---|---|
| **文件夹信箱** | 共享云盘文件夹，一条消息一个文件 | 协调者 ↔ 聊天模型做调研与分析 |
| **分区文档信箱** | 一份共享文档，固定分区（待领 / 结果 / 反馈 / 关闭） | 只能通过文档连接器触达的智能体 |
| **Git 信箱** | 私有仓库，消息即提交文件，任务可用 Issue 承载 | 本来就住在代码托管平台上的编码智能体 |

任何通道旁都可以加一个**通知哨兵**（例如邮件监听）：回执一到就提醒协调者，人就不用一直刷面板了。

## 核心理念

1. **一条消息 = 一个文件，永不修改。** REQUEST、ACK、RESULT、CLOSE 是四个独立文件，用同一个 TaskID 串起来。
2. **每个任务有 ID、有生命周期。** `QUEUED → ACKED → DONE → CLOSED`（另有 BLOCKED 与重排分支，见 PROTOCOL §4/§6）。ACK 只是认领；请求方核验证据、写下 PASS 关闭，任务才算完成。
3. **授权范围写在信封上。** 每个任务声明：可触碰的范围、已预先授权的动作、以及必须过**人工闸门**的动作（登录、安装、付款、发布、业务写入、敏感数据）。
4. **认回执，不认口头。** 结果以 RESULT 文件为准：做了什么、何时、谁做的、证据在哪。
5. **轮询是特性，不是缺陷。** 固定轮询间隔（如每 15 分钟）让每个参与方的行为可预期、可审计。对时延敏感的工作不要走信箱，走实时会话。

## 快速开始

1. 建一个所有参与智能体都能访问的共享文件夹（或文档、或私有仓库）；
2. 按 [PROTOCOL.md](PROTOCOL.md) 约定信封格式与生命周期；
3. 用 [`templates/REQUEST.template.md`](templates/REQUEST.template.md) 写一个任务文件，放进信箱；
4. 接收方轮询发现任务 → 写 ACK 认领 → 执行 → 写 RESULT 文件（同一 TaskID）；
5. 请求方核验证据，写 CLOSE 文件，给出 PASS 或 FAIL 裁定。

把任何内容推到公开副本之前，先跑一遍自查脚本：`bash scripts/check-secrets.sh`。

## 它不是什么

- 不是实时总线。需要亚分钟级协同，请用 API 或共享运行时。
- 不是安全边界。任何对信箱有写权限的人都能投递任务——信箱务必保持私有，人工闸门清单务必短而明确。
- 不是判断力的替代品。协议只负责搬运任务，做什么值得做，仍由人决定。
